## 2. The starting network

*Sources:* ../cifar_cnn.py (build_model, MEAN/STD); ../runs/baseline/last.pt via tools/extract_static.py

**cnn-1** — The network we started with is a small convolutional network from class, with 545,098 trainable parameters, which are the numbers it adjusts while it learns.

> Visual: Full architecture strip: 3@32² → 32@32² → pool → 64@16² → pool → 4096 → 128 → 10; parameter breakdown.

**cnn-2** — Before anything else, every pixel value gets divided by 255, and then each color channel has its dataset average subtracted and gets divided by its standard deviation, which puts the channels on a similar scale around zero and usually makes training better behaved.

> Visual: Equation x̂ = (x − μ)/σ with the real CIFAR channel statistics and one real frog pixel worked through.

**cnn-3** — The first real layer is a convolution. A filter is a 3 by 3 window over all three color channels, so it has 27 weights plus a bias. At each position it multiplies the values under it by its weights and adds everything up, and this panel is that exact calculation from our trained model. Slide the same window across every position and you get a new 32 by 32 map.

> Visual: Window moves to row 14, col 15; real multiply-sum (0.6256, matches the model); 'Slide' starts the sweep and the real output map fills in.

**cnn-4** — The filter uses the same weights at every position, so a pattern it learns in one spot can be picked up anywhere else in the image. That's also why all 32 filters in this layer only need 896 parameters.

> Visual: Several windows linked to one shared kernel; 32 × 28 = 896.

**cnn-5** — These are the actual filters our baseline learned, and the maps they produce for this frog. Nobody designed these weights by hand, training found all of them.

> Visual: Real conv1 filters and activations from ../runs/baseline/last.pt.

**cnn-6** — After the convolution, ReLU replaces every negative number with zero, and then 2 by 2 max pooling keeps only the biggest value in each 2 by 2 block, which cuts the maps from 32 by 32 down to 16 by 16.

> Visual: Example number grid (illustrative): negatives → 0, then 2x2 max; real map before/after pooling.

**cnn-7** — The second block does the same thing with 64 filters, but now each filter reads all 32 maps from the first block, so it can combine simpler patterns into more complicated ones. Pooling then takes everything down to 8 by 8.

> Visual: Real conv2 activations; slab shrinks to 8x8 on 'Pooling'.

**cnn-8** — That leaves 64 maps of 8 by 8, which is 4,096 numbers. We flatten them into one long list, pass it through a hidden layer of 128 units, and the last layer gives us ten scores, one for each class.

> Visual: Slab dissolves into a 4096 column, particles flow to 128 then 10; dense-layer parameter count.

## 3. How it learns

*Sources:* ../runs/baseline.log; ../runs/baseline/last.pt (logits, loss slice); ../research-log.md

**learn-1** — Those ten scores are called logits. They can be any size, positive or negative, so on their own they aren't probabilities yet.

> Visual: Real logits for the frog as signed bars.

**learn-2** — Softmax is what turns them into probabilities. You exponentiate each score, which makes everything positive, and then divide by the total so they all add up to one.

> Visual: Softmax equation; bars morph into real probabilities on 'exponentiate'.

**learn-3** — Here the model puts about 74 percent on frog and about 14 percent on cat, so it's mostly right but not very sure.

> Visual: Frog probability highlighted.

**learn-4** — To train it, we need one number for how wrong it was, and that's the cross-entropy loss, the negative log of the probability it gave the correct class. Confident and right costs almost nothing, this frog only costs about 0.31. Confident and wrong costs a lot, so giving the right answer just 2 percent would cost about 3.9.

> Visual: L = −log p_y curve with the real frog point, then the labelled example point p = 0.02.

**learn-5** — One detail about PyTorch here. The model itself only outputs logits, and PyTorch's cross-entropy loss applies log-softmax internally, so softmax is just how we read the outputs, it isn't an extra layer in the model.

> Visual: nn.CrossEntropyLoss(z, y) = −log softmax(z)_y; no softmax layer in build_model.

**learn-6** — Backpropagation then uses the chain rule to work backwards from the loss through every layer, and gives each of the 545,098 parameters a gradient, which says how the loss would change if that parameter moved a tiny bit.

> Visual: Forward particles, then gradient pulses flow backward; chain-rule equation; schematic tag.

**learn-7** — Gradient descent moves every weight a small step against its gradient, with the learning rate setting the step size. This surface is a real slice of the loss around our trained baseline, along two random directions in weight space, and the dashed path is just an illustration of stepping downhill, not steps we recorded.

> Visual: Measured 25x25 loss slice (tools/extract_static.py); dashed path labelled illustrative on 'path'; update rule w ← w − η∇L.

**learn-8** — Each step uses a batch of 64 images, so one full pass through the 50,000 training images, which is called an epoch, takes 782 steps.

> Visual: 782 batch tiles fill up one epoch.

**learn-9** — We trained for ten epochs with a learning rate of 0.01, and this baseline reached 63.68 percent test accuracy. That's a lot better than the 10 percent you'd get from guessing, but it's still wrong on more than a third of the test images.

> Visual: Real per-epoch test curve from ../runs/baseline.log; chance line at 10%.

## 4. Bigger batches

*Sources:* ../BENCHMARKS.md; ../runs/tuned-b512.log; ../runs/step-matched-b512.log

**batch-1** — The first thing we tried was making training faster. At batch size 64 the GPU was only busy about 42 percent of the time, so we tried batch size 512, and ten epochs finished in 5 seconds instead of 22.

> Visual: Two lanes: batch 64 vs batch 512; timers 22.39 s vs 5.21 s; mean GPU utilization 41.6% vs 89.4%.

**batch-2** — The catch was that test accuracy dropped to 48.58 percent. With the same number of epochs, a batch eight times bigger also means eight times fewer weight updates, 980 instead of 7,820 at the same learning rate, so our guess was that the model just hadn't taken enough steps.

> Visual: Step dots: 7,820 vs 980; '8× fewer steps' appears on 'eight'.

**batch-3** — To check that, we trained batch 512 for 80 epochs, which gives 7,840 updates, almost exactly the same as the baseline, and that run reached 67.67 percent. That fits the step count explanation, but it isn't a perfectly clean test, because this run also went through eight times as many images.

> Visual: Real test curves plotted against optimizer updates; 67.67 labelled on 'reached'.

**batch-4** — So with matched steps, batch 512 ended up about 4 points higher, and it took 37 seconds instead of 22. These are single runs with one seed each, so the exact gap isn't something to lean on too hard.

> Visual: Image-pass bars: 0.5M vs 4M; 22.39 s vs 36.85 s.

## 5. Augmentation on the small network

*Sources:* ../runs/augmentation/comparison.json + comparison.md; ../augmentations.py

**aug1-1** — Next we tried data augmentation, which means every time the network sees a training image, it gets a randomly changed version of it. Flip it left to right half the time, or pad the border with 4 black pixels and crop a random 32 by 32 window, which shifts the image around a little.

> Visual: Real horse: flip, pad with 4 black pixels, crop windows.

**aug1-2** — A horse facing left is still a horse, so the label stays the same, and the hope is that the network learns to ignore things like direction and small shifts, which is called invariance. Seeing varied views of each image also makes it harder to just memorize the exact training images, so it works as a kind of regularization.

> Visual: All views map to one label.

**aug1-3** — We tested 15 different recipes on the small network with three seeds each, measuring test accuracy. No augmentation got 67.96 percent. Flip on its own helped a little, 68.77, and it improved every seed. Crop plus flip actually hurt, down to 66.38, and everything we added on top of it did worse than no augmentation.

> Visual: Real bar chart of all 15 recipes with seed error bars; none / flip / crop+flip light up when spoken.

**aug1-4** — Then there's the gap between training and test accuracy, which went from about 7 points without augmentation to under 1 with crop plus flip. A smaller gap can mean useful regularization, or it can just mean the model learned less, and since test accuracy went down, the gap alone doesn't show an improvement. Our best guess is that this small network on a short recipe couldn't fit the harder data, but we didn't test that.

> Visual: Real train/test curves; gap 7.33 vs 0.74 points.

**aug1-5** — This suite also looked at the test set over and over, so these results are exploratory.

> Visual: Caveat tag.

## 6. A stricter setup

**recipe-2** — We also switched to a stronger training recipe: batch 128, SGD with momentum and weight decay, batch norm after every convolution, and a learning rate that warms up for 5 epochs, then follows a cosine curve down over 160 epochs. ## 7. Adding depth

**depth-1** — Next we wanted to know if more convolutions would help. We kept the same two stages, the same pooling, and the same classifier, and only stacked more convolutions inside each stage, from 2 up to 32.

> Visual: Architecture grows 2 → 4 → 8 → 16 → 32 convolutions.

**depth-2** — Each extra 3 by 3 layer lets a unit see a slightly bigger part of the image, 5 by 5 after two layers, then 7 by 7 after three, and it gives the network more steps to build up complicated features.

> Visual: Receptive field grows on the frog (schematic).

**depth-3** — On validation, two convolutions got 78.27, four got 84.53, eight got 86.90, and sixteen got 87.17, so the gains were shrinking but still positive. Then at 32 convolutions it dropped to 83.08, and all three seeds got worse.

> Visual: Real validation accuracy vs depth with seed spread; points appear on the spoken depths; the 32-layer point falls.

**depth-4** — Every depth reached 100 percent training accuracy, so the 32 layer network could still fit the training set, it just did worse on images it hadn't seen, and these runs alone can't tell us whether that came from optimization, generalization, or both.

> Visual: Real final train accuracy 100% for all depths; real curves 16 vs 32.

**depth-5** — That's different from the original ResNet paper, where deeper plain networks had higher training error. Ours trained fine and fell on validation. ## 8. Residual connections

*Sources:* ../depth_cnn.py (Block.shortcut zero-pad); ../runs/depth/comparison.json; https://arxiv.org/abs/1512.03385

**residual-1** — A residual block keeps the same two convolutions, but adds a shortcut that carries the block's input around them and adds it back at the end.

> Visual: Plain block and residual block side by side; shortcut draws.

**residual-2** — So the main path computes F of x, which is conv, batch norm, ReLU, conv, batch norm, and the block outputs ReLU of F of x plus the shortcut.

> Visual: y = ReLU(F(x) + shortcut(x)).

**residual-3** — When the number of channels doubles from 32 to 64, our shortcut just pads the input with 32 channels of zeros. That adds no learned weights, so every residual network has exactly the same number of parameters as its plain version, and the two start from the same initial weights.

> Visual: 32 channels + 32 zero channels → 64; 1,239,274 parameters at 32.

**residual-4** — The usual explanation is that if a block should barely change its input, a plain block has to learn to copy it through two convolutions, while a residual block just pushes F toward zero. During backprop, the shortcuts also give the gradient a direct path back. These pictures are schematics, not measurements.

> Visual: Vector diagram x + F(x) = y, then gradient pulses on both paths (schematic).

**residual-5** — Residual 4 got 83.77 on validation, eight got 86.67, sixteen got 86.85, and thirty-two got 87.20.

> Visual: Real residual line joins the plain line point by point.

**residual-6** — So at 32 layers the shortcuts clearly mattered, about 4 points over plain 32. But residual didn't beat plain at 4, 8, or 16, and residual 32 is only 0.03 points above plain 16, well inside the variation between seeds. It still had the highest average, so it was selected, and on the test set it scored 86.43 percent, plus or minus 0.49.

> Visual: Gap at 32 highlighted; spread band; test card.

## 10. CIFAR ResNet-18

*Sources:* ../followup_cnn.py (build_model); torchvision 0.22.1 resnet18; ../runs/followup/resnet18-crop-flip/seed-*/metrics.jsonl

**resnet-1** — Last, we tried ResNet-18, which is a much bigger residual network, adapted for CIFAR and trained from random weights, so there's no pre-training on ImageNet.

> Visual: Code card: resnet18(weights=None), 3×3 stride-1 stem, maxpool = Identity.

**resnet-2** — The standard version starts with a 7 by 7 stride 2 convolution and a max pool, which is built for big ImageNet photos and would shrink our images to 8 by 8 before the blocks even start, so we swapped in one 3 by 3 stride 1 convolution and removed the max pool.

> Visual: Stem slab; ghosted ImageNet stem crossed out on 'swapped'.

**resnet-3** — After that come eight basic residual blocks, two per stage, with 64, 128, 256, and 512 channels. The first stage stays at 32 by 32, and each of the next three halves the resolution, so the maps go from 32 to 16 to 8 to 4. Where the shape changes, the shortcut is a learned 1 by 1 convolution with batch norm instead of zero padding.

> Visual: Blocks appear stage by stage on the spoken channel counts; resolutions on the spoken sizes; amber projection shortcuts.

**resnet-4** — At the end, global average pooling turns each 4 by 4 map into a single number, and one linear layer maps those 512 numbers to the ten classes, with no 128 unit hidden layer like before.

> Visual: 512x4x4 → 512 → 10.

**resnet-5** — The 18 comes from counting the layers with weights along the main path. The stem is one, the blocks have 16 convolutions, and the classifier makes 18. The projection shortcuts aren't counted, by convention.

> Visual: Counter 1 + 16 + 1 = 18, synced to 'stem', '16', 'classifier'.

**resnet-6** — So compared with residual 32, a lot more changed than the layer count. ResNet-18 keeps higher resolution for longer, has many more channels, learned shortcuts, a global pooling head, and about 11.2 million parameters, roughly nine times as many. It also trained for 200 epochs instead of 160, so this compares whole recipes, not just architectures.

> Visual: Side-by-side comparison card; rows appear as each difference is spoken.

**resnet-7** — Across three seeds, it averaged 95.77 percent validation accuracy over the last ten epochs, plus or minus 0.11, compared to 93.74 for residual 32 with the same augmentation.

> Visual: Real ResNet-18 validation curve vs residual-32 crop+flip; final-10 window.

## 11. What the results support

**end-1** — When the queue finished, it picked ResNet-18 with crop plus flip based on validation, and only then did we run that model on the test set. It got 95.21 percent test accuracy, plus or minus 0.02 across the three seeds.

> Visual: Queue status from runs/followup/queue-state.json at snapshot; selected model and its test score.

**end-4** — If we did this again, we'd keep comparing runs by optimizer steps and not just epochs, deciding on validation across seeds, not treating a smaller train-test gap as an improvement by itself, and retesting a technique when the model or recipe changes, since crop plus flip went from hurting to helping.
